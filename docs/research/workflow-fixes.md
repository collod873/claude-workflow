# Workflow Fixes: what's broken and what to do

_Session findings, 2026-07-28. Companion to `skill-design-principles.md`._

Repos looked at: `collod873/Lumaria`, `collod873/PWPP-Projects`.
Skills looked at: wayfinder, triage, to-tickets, to-spec, implement, drain, code-review.

---

## 1. Quality is broken because of hooks, not skills

**Lumaria** has guard hooks. A Stop gate that lints your changes and won't let the turn end dirty, plus 3 PostToolUse guards.

**PWPP** has none. Its only PostToolUse hook is an `echo`:

```
echo 'Verify: use the relevant PWPP subproject workflow or check the changed docs
directly. This parent workspace has no single shared verification command.'
```

That is false. `pytest.ini` line 1 says:

> `# The one true test command: python3 -m pytest -q from the repo root.`

And that file exists **because tests already rotted once**: it names #254, #199 (a stale assertion left red for weeks), and #164. You fixed this at the config layer. The hook layer never got the memo and still tells every agent there's nothing to run.

So in PWPP nothing checks anything, ever. Skills only *suggest*. Hooks *force*.

| | Lumaria | PWPP |
|---|---|---|
| Stop gate | `stop-gate.sh` (lints changed files, blocks turn, one forced retry, has own test file) | **none** |
| PostToolUse guards | `decoration-rail.sh`, `jscpd-guard.sh`, `status-badge-guard.sh` | **one `echo`** |
| Gate command | exists | exists, nothing runs it |

**Do:**
- Port `stop-gate.sh` to PWPP: swap eslint/biome for `python3 -m pytest -q` scoped to changed subtrees. Keep the block-once-then-hand-back circuit breaker; that design is already right and already tested.
- Delete the lying `echo` hook.
- Port `jscpd-guard.sh` to PWPP. Two of PWPP's six standards are duplication rules: *"byte-identical block in more than two `*-roster-fetcher.py` files"*, *"the same literal set or predicate byte-identical in two files."* Lumaria already owns the tool that checks those.

`CODING_STANDARDS.md` already says to do this: *"can a lint rule enforce this? If yes, add the rule instead, no entry."* You wrote the policy. PWPP has nowhere to put the rules.

**This is the big one. Do it first.** Small, testable, stops the bleeding tonight.

## 2. You never need to triage

`collod873` opened **297 of 300** Lumaria issues and **293 of 293** PWPP issues. There is no second party.

Triage was written for a repo with strangers in it:

- `needs-info`: *"waiting on **reporter**"*, template addressed to `@reporter`
- every comment carries `> *This was generated by AI during triage.*`
- discovery *"surfaces only **external** PRs"*
- step 2: *"Recommend… **Wait for direction.**"*

All of that arbitrates between a reporter and a maintainer. You're both. The disclaimer warns a reader who doesn't exist. `needs-info` waits on a person sitting in the session.

It's not that triage is too cautious; it's a **multi-party skill running on a single-party tracker.**

**One test the agent applies:**

> Is there an undecided thing inside this issue?

| Answer | Outcome |
|---|---|
| **No**: it names a job | `ready-for-agent` + wire its edges. No ask. |
| **Yes**: it holds an open question | needs your brain → grilling / wayfinder ticket |

"Needs another issue to go first" is **not** an escalation. It's a `blockedBy` edge. Agent records it and moves on.

`needs-info` stops being a gate and becomes a batched question queue you answer whenever.

## 3. Order is invisible, and that's the real friction

Labels are visible in the GitHub UI and they still don't hold the order. **File overlap** does, and nothing writes it down.

Proof from the tracker:

- #297's body correctly says it has no logical dependency on #295: *"it needs no `id_scheme` column and no schema change at all."*
- But #295 scope item 3 is *"the inventory-vs-coverage id cross-check in `freshness_report.py`"*, which is #297's entire scope.
- Verified the file exists: `Correctional Institutions/coverage/_scripts/freshness_report.py`.
- Verified the graph: **no edge between them.** Neither is the other's parent, neither blocks the other.

Hand both to `/drain` → dispatched in parallel → merge conflict. Run them by hand in the wrong order → #295 rewrites what #297 just shipped. Invisible in the UI no matter how long you stare. Multiply by 11 `ready-for-agent` issues.

**Do:** auto-triage wires the edges. Then order stops being a decision; drain reads the frontier and runs 3 at a time.

**Also:** drain requires a `PRD:` spec today. The 11 `ready-for-agent` PWPP issues have no parent (checked #297, #295, both `NO PARENT`). Let drain take a label query or plain issue list instead. The spec is only used for finding tickets, the `Part of #<n>` breadcrumb, and the close comment, all of which have obvious substitutes. Inventing a fake spec to satisfy a skill is ceremony.

**Also:** #295's scope item 3 is stale; #297 owns that work now. Real edit someone should make.

## 4. Wayfinder has no ending

Trace it literally:

| Session | You type | What happens |
|---|---|---|
| 0 | `/wayfinder <idea>` | 2 grillings → map + N tickets |
| 1..N | `/wayfinder <map>` | resolves exactly 1 ticket, may spawn more |
| N+1 | `/wayfinder <map>` | **frontier empty. Nothing to pick.** |

There is no step N+1 in the text. "Work through the map" ends at step 5 (add tickets, graduate fog). It never loops back to ask *is the way clear now?*, never closes the map, never hands off. The skill says "the map is done when the way is clear" in prose, and no step evaluates that sentence.

Three effects, which are the disorientation:

- **No progress signal.** Every session resolves one ticket and reports nothing about the remainder.
- **No predictable end.** Fog *creates* tickets as you resolve them, so the count can go 8 → 9 → 7 → 11.
- **No handoff.** If the way *is* clear and Destination says "a spec," nothing runs `/to-spec`. That knowledge lives only in your head.

**Do:**
- Add the closing step.
- Destination type becomes a **label** set at charting; step 1 already forces the judgment, then writes it as free text nobody reads again.

  | Label | Terminal |
  |---|---|
  | `wayfinder:dest-spec` | run `/to-spec`, close the map |
  | `wayfinder:dest-decision` | close the map; decision already in Decisions-so-far |

- **Delete execute-mode.** Confirmed as drift, not desire: it was easy, so it became the default. It produced the 39 unreviewed commits. Wayfinder ends at "decided"; the build happens after, in the path where the gate lives. Same work, just past the map instead of inside it.

Wayfinder gets **smaller**, not bigger. It is not becoming a god-skill; one module edited for several unrelated reasons is Divergent Change.

**One job each:**

```
fuzzy ──▶ decided ──▶ specified ──▶ sliced ──▶ built ──▶ checked
   wayfinder    to-spec     to-tickets    implement    code-review
                                            /drain
```

A terminal is a **pointer**, not an implementation. Wayfinder doesn't grill, build, drain, or review. It ends, and the ending names the next skill.

## 5. Review is a definition of *closed*, not a schedule

- **Spec axis** = the close gate. A ticket can't close until each acceptance criterion is checked against the observed diff. Runs as a **fresh subagent** whenever the context that wrote the diff would be doing the checking (no marking your own homework); inline is fine when the checker is already fresh (drain's foreman, a new session).
- **Standards axis** = per batch, never per ticket. Its real output is *standards authorship* (proposing lint rules and `CODING_STANDARDS.md` entries) not defect-finding. That's why it scored 0 defects. Skipping it on one-offs isn't a compromise, it's correct.

One rule, all paths. Decidable from observable state, so a hook can enforce it without knowing which skill ran.

## 6. Where the contracts live

`~/.claude/contracts/` in chezmoi. Neutral third home: `/sync-skills` never touches it, drain already lives in chezmoi, and a hook can read a file more easily than a skill.

Skills in `~/.agents/skills` point at it by absolute path. **Each pointer needs an `UPSTREAM.md` row with a grep marker** or `/sync-skills` clobbers it.

## Order of work

| # | What | Size |
|---|---|---|
| 1 | PWPP hooks: stop gate, kill the echo, port jscpd | small, 1 repo |
| 2 | Auto-triage + wire edges | medium |
| 3 | Drain takes a list instead of requiring a spec | tiny |
| 4 | Wayfinder: kill execute-mode, add dest label + closing step | small |
| 5 | Review contract | small |

Hooks first and separately: ~2 files in one repo, testable the way `writing-great-hooks` demands (four cases, driven from Python), and it fixes the actual quality leak. The skill work is bigger and can't be verified as cleanly; doing them together means neither gets proven.

---

## The reframe

**Quality is hooks. Throughput is skills.** The attempt was to solve the first with the second.

Everything designed at the skill rung is a *strong steer*: the agent may not comply. A hook is code the harness runs. Drain's quality never came from `/code-review`; it came from *run the gate after every merge, the verdict is the exit status you observed.*
